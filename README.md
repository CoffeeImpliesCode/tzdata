# tzdata as a Zig SDK

The IANA Time Zone Database — upstream `eggert/tz`, release `2026e`, commit
`039ef27cc5f062a2055cb67435d6d71adbefd27d` — with a Zig 0.16 build around its
unmodified C sources and zone data.

tzcode is compiled with upstream's documented private-`time_t` mode, so every
externally visible entry point carries a `tz_` prefix: this library cannot
shadow libc's `localtime`, `mktime`, `tzname`, `timezone`, `daylight` or
`strftime`.  The build compiles its own database with its own `zic` and
publishes it to `share/zoneinfo`, which is also the `TZDIR` compiled into the
library, so `Zone.open("Europe/Berlin")` works in a dependent package with no
further wiring.

* `README.zig.md` — the Zig interface: commands, module API, ownership, symbol
  isolation, where the data is, platform notes.
* `README.upstream.md` — upstream's `README`, preserved byte for byte (SHA-256
  `38b3f33eaddff624727c5bb238542bf448b1b5f446a31085c1ce34942819d328`, the
  digest `PROVENANCE.sha256` records for `README`).
* `UPSTREAM.md`, `NOTICE.md`, `FORK-LICENSE.md`, `FORK-NOTES.md`,
  `CHANGELOG.md`.

## Native-source deviations

**None.**  No upstream C source, header, data file, manual page, script or
licence file has been changed.

The one upstream file this fork modifies is `.gitignore`, which keeps every
upstream pattern and appends negations so the fork's subdirectories and
dotfiles are visible to Git and to Zig's package hashing — upstream's file
ignores every subdirectory (`*/`) and every dotfile (`.*`).  Its upstream
content is recorded in `CHANGELOG.md` entry 1 as
`sha256 8607841b6e6f8525f49013d9592a32775d412e0a6e80ec6510f4d786493cb36b`;
that is a prior record, not a gate result, because `PROVENANCE.sha256` covers
only the 53 unchanged files.

Configuration is not a source change: the fork compiles the unmodified sources
with preprocessor options upstream documents in `Makefile` and `private.h`,
plus `-Dtime_tz=time_t`.  The complete list and each value's reason are in
`README.zig.md`, "Platform notes".

## Native-build deviations

**Dated history:** `CHANGELOG.md` entries 1–15 (2026-10-03 and earlier) and
`FORK-NOTES.md` sections 1–22 record why each of these exists.  This migration
adds `CHANGELOG.md` entry 16 and `FORK-NOTES.md` sections 23–29.

### The build system is replaced, not wrapped

Upstream's `Makefile` is not used, and neither are CMake or autotools.  There
is no build-time download: the C sources and the zone data are both in this
tree.  `version.h` and `tzdir.h`, which `Makefile` generates and does not
ship, are regenerated by `build.zig` with the same content shape, so the
upstream sources compile without being edited (`FORK-NOTES.md` § 3).

### The database pipeline skips two upstream preprocessors

`zic` is fed the zone sources directly: `africa`, `antarctica`, `asia`,
`australasia`, `backward`, `etcetera`, `europe`, `factory`, `northamerica`,
`southamerica` — the Makefile's `$(TDATA)`.  A stock upstream `make` instead
derives `main.zi` with `ziguard.awk` and `zishrink.awk` (`Makefile:745-764`)
and compiles that.  Neither runs here, which is upstream's own `check` input
list (`Makefile:1208-1212`), so **the installed tree can differ from a stock
`make install`** for zones those scripts rewrite or drop, and no gate compares
the two.  No leap-second database is generated, matching upstream's
`REDO=posix_only`: `Zone.toPosix` and `Zone.fromPosix` return their input
(`FORK-NOTES.md` § 4).

### Symbol isolation is upstream's, applied unconditionally

`-Dtime_tz=time_t` is upstream's documented private-`time_t` mode.  In that
mode upstream renames every externally visible identifier with a `tz_` prefix,
so no source patch is needed, and `zic` is unaffected because it `#undef`s
`time_tz`.  `HAVE_TZNAME` and `USG_COMPAT` are pinned per target branch rather
than guessed from the libc headers and mirrored into the translation step, so
`tzdata.c` never declares a symbol the library cannot link
(`FORK-NOTES.md` § 20).

### `TZDIR` is the installed database

`zic` writes the TZif tree into a digest-named directory in the build cache,
and an install step publishes it to `<install prefix>/share/zoneinfo`.  **That
directory is the compiled-in `TZDIR`**, and the library step depends on the
publish step, so the compiled path, the installed database and what a dependent
resolves a plain name against are always the same (`FORK-NOTES.md` § 25).

`-Dtz-dir` cannot choose the path: a value other than this invocation's
installed database directory is a configure-time failure naming both paths.
`--prefix` is how you choose it.

### Static and shared delivery

`-Dlinkage=static` (the default, and this SDK's existing policy) builds
`lib/libtz.a`.  `-Dlinkage=dynamic` builds a real shared object from the same
four translation units, with `.pic` set on the library module and the same
`tz_*` export set; the static branch leaves `pic` at the compiler default, so
the existing static objects are unchanged.  Zig names the shared artefact per
target: `lib/libtz.so`, `lib/libtz.dylib`, or `tz.dll` plus `tz.lib` on
MS-Windows, where a generated module-definition file lists the exports because
a COFF DLL exports nothing without one.  `check` does not fold the option in:
it installs nothing, so folding it in would make it answer a different
question.

Neither variant is a wholly static closure.  Both link libc.

### The install tree

| Path | Content |
| --- | --- |
| `lib/libtz.a`, or the shared form above | the namespaced tzcode library |
| `lib/pkgconfig/tzdata.pc` | relocatable link metadata: `prefix` from the file's own location, `Version` from `-Dtz-version`, `Libs: -L${libdir} -ltz`, no `Libs.private`, and one `-D<NAME>=1` per enabled macro in `Cflags` |
| `bin/zic` | the zoneinfo compiler, a host program on every target |
| `include/tzdata.h`, `include/tzfile.h` | aggregate public header, and upstream's on-disk header |
| `share/zoneinfo/**` | the compiled TZif tree |
| `share/zoneinfo/{iso3166.tab,zone.tab,zone1970.tab,zonenow.tab}` | upstream's zone lookup tables |
| `share/man/man3/{newctime.3,newtzset.3}`, `man5/tzfile.5`, `man8/zic.8` | the manual pages upstream's `install` rule installs |
| `share/licenses/tzdata/{LICENSE,NOTICE.md,FORK-LICENSE.md,UPSTREAM.md}` | the licence material |

Deliberately absent:

* **`zdump`**, **`date`** and **`tzselect`.**  The sources ship — `zdump.c`,
  `date.c`, `tzselect.ksh` — but no step compiles them, so `zic` is the only
  tool artifact and `dep.artifact("zic")` the only tool a dependent reaches.
* **`leapseconds` and `tzdata.zi`.**  Upstream installs both beside the TZif
  files, but both are awk-derived from shipped sources (`Makefile:790-792`,
  `745-764`), so no file in this tree is the file to install.  Nothing here
  consumes either: the library reads leap seconds from the TZif files, which
  is what `TZ_RUNTIME_LEAPS=1` selects, and `zic` is fed the raw `$(TDATA)`
  sources.  `FORK-NOTES.md` § 29 records the decision.

## Support matrix

Zig 0.16.0.  Host runs on x86-64 Linux; `check` compiles six further targets.

| Command | What it does |
| --- | --- |
| `zig build` | builds `tz` and `zic`, compiles and publishes the database, installs everything in the table above into `zig-out/`.  `--prefix <dir>` chooses the prefix and therefore the compiled-in `TZDIR` |
| `zig build test` | the behavioural suite; runs `zic` for fixtures, reads the published tree |
| `zig build smoke` | converts fixed timestamps in zones opened by plain name against independently known civil times |
| `zig build check` | compiles library, facade, smoke and tests for the six targets below; runs nothing, installs nothing |
| `zig build provenance` | verifies all 53 recorded upstream files against `PROVENANCE.sha256`, and that `README.upstream.md` is still the preserved copy of upstream's `README` |
| `zig build consumer` | runs the separate `consumer/` package, or installs it when this host cannot execute the selected target |
| `cd consumer && zig build run` | the same consumer run without the parent build |

Options: `-Doptimize=`, `-Dtarget=<triple>`, `-Dlinkage=static|dynamic`,
`-Dtz-version=<release>`, `--prefix`, and `-Dtz-dir=` as an assertion of this
invocation's installed database directory.

Compile-only targets (`build.zig:81-89`): `x86_64-linux-gnu`,
`aarch64-linux-gnu`, `aarch64-macos`, `x86_64-windows-gnu`,
`riscv64-linux-gnu`, `wasm32-wasi`.

**Verification state.**  `CHANGELOG.md` entry 14 records observed gates for
Zig 0.16.0 on native Linux x86-64 before this migration: native build, 23/23
Debug and ReleaseSafe tests, smoke, six-target compile check, consumer run and
a 53-file provenance pass; entry 15, dated 2026-10-03, adds the install step
and the independent module example.  Those describe the tree as it stood
before this migration and are not evidence for the delivery it added.  **No
gate has been run against the static/shared split, the moved `TZDIR`, the

`build_only` is compiled-not-run and is **never** counted as a test pass: 21 of
the 53 cells are coverage of the compiler, not evidence about behaviour.

**The twelve red cells are this fork's own refusals, not defects and not
translator accidents.**  All twelve stop in `refuseTarget` (`build.zig:903-910`)
with `error.UnsupportedTarget`, before a compiler is invoked, and each names
the target's own libc:

* nine NetBSD cells — `aarch64-netbsd`, `aarch64_be-netbsd`, `arm-netbsd`,
  `armeb-netbsd`, `mips-netbsd`, `mipsel-netbsd`, `powerpc-netbsd`,
  `x86-netbsd`, `x86_64-netbsd` — refused because `` `zig translate-c` cannot
  read this libc's `sys/cdefs.h`, which every NetBSD header reaches``
  (`build.zig:781-782`).
* three 32-bit OpenBSD cells — `arm-openbsd`, `powerpc-openbsd`,
  `x86-openbsd` — refused because "the translator's `size_t` and this libc's
  differ at 32 bits" (`build.zig:842-843`).  The 64-bit half of OpenBSD is not
  in this table.

These are **intentional**, and the build cannot drift away from them: the table
`refusalFor` returns is re-derived on every invocation against the rows `check`
walks (`build.zig:912-927`), so a row this build refuses can never sit in that
matrix unnoticed.  A cell that goes red because the build refused it is an
observed boundary, not coverage.

**What this matrix does not cover.**  The 53-cell run predates the later
build-graph, header and normalization edits; its `source_unchanged: true`
speaks only to its own run, and those edits are not claimed to be covered by
it.  It also says nothing about a `-Druntime=true` **consumer install**: the
dependency's library is not linked on that route, so the TZif tree is not
published through that edge and the install delivers the executable alone.
That is a pre-existing property of the graph, unchanged here and not a new-scope
fix (`FORK-NOTES.md` § 37, "The consumer step asked a foreign target to run").

Platform boundaries that are design facts:

* `zic` is a host program on every target, including a cross build.  WASI
  lacks the `umask` and signal APIs its source needs, so the WASI library,
  facade, smoke and tests are compiled from a database a host `zic` produced.
* On `x86_64-windows-gnu` `struct tm` has no `tm_gmtoff` or `tm_zone`, so
  `Tm.utcOffset` answers null there while `Zone.utcOffset` still answers,
  deriving the offset through `tz_timegm`; `tz_tzname`, `tz_timezone` and
  `tz_daylight` are neither emitted nor declared; `asctime_r`/`ctime_r` are
  static functions upstream; and `formatAlloc`'s `%Z` and `%z` render empty.
* There is no system-library mode: no installed library exports `tz_tzalloc`,
  `tz_localtime_rz`, `tz_mktime_z` or `tz_time2posix_z`, so translating this
  header against an installed libc would be the header/ABI mismatch the fork
  contract forbids (`FORK-NOTES.md` § 9).

## Consumption

### Zig

```zig
// build.zig.zon
.dependencies = .{
    .tzdata = .{ .path = "../tzdata" },
},
```

```zig
// build.zig
const dep = b.dependency("tzdata", .{ .target = target, .optimize = optimize });
exe.root_module.addImport("tzdata", dep.module("tzdata"));
```

The native library is linked for you; do not add `tz` to the same build again.
`dep.artifact("zic")` compiles a consumer's own zone source, which is what
`consumer/` does.  The full surface, with ownership and lifetime rules, is in
`README.zig.md`.

### Nix

`package.nix` is one injected function returning one derivation;
`flake.nix` calls it once per linkage.

```sh
nix build .#static     # lib/libtz.a, also .#default
nix build .#shared     # lib/libtz.so
```

`package.nix` is source-only: no workspace import, no host path, no build-time
download, no `../` sibling.  It passes `--prefix "$out"`, which is what makes
`$out/share/zoneinfo` both the installed database and the compiled-in `TZDIR`,
and repeats `-Dtz-dir="$out/share/zoneinfo"` as an assertion of that
resolution.  It writes nothing else: `build.zig` installs every artifact,
header, table, manual page, licence file and the pkg-config metadata.  Its
check phase runs `zig build provenance` over the filtered source.

The nixpkgs input is pinned in `flake.nix`, which inlines the revision in
`inputs.nixpkgs.url`, and locked by `flake.lock`: that file exists here, locks
that same revision, and is named in `.paths`, so a fetched tarball resolves the
input without network access.  `devenv.lock` does not exist here — `devenv.yaml`
pins `cachix/devenv-nixpkgs` and leaves that lock to the driver.

### Development environment

`devenv` is canonical — not the Nix packages, and not `nix develop`, which
this flake deliberately does not offer.

```sh
direnv allow      # .envrc is `use devenv`
devenv shell
```

Inside the shell, devenv puts these on PATH: `tz-build`, `tz-test`, `tz-smoke`,
`tz-check`, `tz-provenance`, `tz-consumer`, `tz-consumer-direct`.  Each one
changes into this checkout before it does anything, so a shell entered from
another directory still answers for this tree.  Every one of them forwards the
flags and step arguments it was given.

Five of them deliver something and therefore take a `--prefix` outside the
checkout: `tz-build`, `tz-test`, `tz-smoke`, `tz-consumer` and
`tz-consumer-direct`.  `zig build test` and `zig build smoke` publish
`share/zoneinfo` through the install step (`FORK-NOTES.md` § 25) and
`consumer/build.zig` declares an install step for its own executable, so each
of the five writes under `$ZIG_LOCAL_CACHE_DIR/tzdata/<script>`;
`$XDG_CACHE_HOME` and then `$TMPDIR` are used when `ZIG_LOCAL_CACHE_DIR` is
unset, and a caller who exported none is told so rather than given a location
this environment has no right to invent.
`TZDATA_PREFIX` overrides the location outright when you want the installed
tree somewhere else.  `tz-check` and `tz-provenance` take no prefix and lose
nothing by not taking one: neither step installs anything.  The `consumer` run
keeps the TZDIR its own dependency installed, because `--prefix` cannot reach
a dependency and `build.zig` forwards it for the consumer's own executable
alone.

The shell carries tools only; the SDK derivations are lazy `outputs.static` and
`outputs.shared`, built with `devenv build outputs.static` /
`devenv build outputs.shared`.  Build caches and any scratch variables are
the caller's: this environment neither sets nor resets them, and the prefix
above is read from the environment rather than written to it.

### C

An installed prefix needs one thing from a consumer —
`pkg-config --cflags --libs tzdata` — and nothing else.

The reason is `include/tzdata.h`: six declarations are gated on four macros,
`TZDATA_HAVE_STRFTIME_L`, `TZDATA_HAVE_POSIX2008`, `TZDATA_HAVE_TZNAME` and
`TZDATA_USG_COMPAT`, that describe the C compile line rather than the header.
They decide whether `tz_strftime_l`, `tz_asctime_r`, `tz_ctime_r`,
`tz_tzname`, `tz_timezone` and `tz_daylight` are declared at all.  The `.pc`
file carries them; guessing them gives either a link failure or a silently
missing declaration (`FORK-NOTES.md` § 28).

No gate in this repository builds an installed C consumer, so that route is
documented and unexercised.

### What this SDK is not

This library is not libc's timezone implementation and its ABI is not libc's.
Every entry point carries a `tz_` prefix from upstream's own renaming mode; a
libc exporting `localtime`, `mktime`, `tzname`, `timezone`, `daylight` and
`strftime` exports **none** of them.  Do not assume that an arbitrary libc
timezone ABI, another vendor's `tzalloc`, or a `zoneinfo` tree from a
different toolchain is equivalent to this SDK's `tz_` API, and note that
tzcode has no versioned ABI at all.  There is no system-library mode.

Under `-Druntime=true` a provider is accepted only after every symbol resolves
and one behavioural check passes: allocate with `tz_tzalloc("")`, convert the
epoch through `tz_localtime_rz`, release through `tz_tzfree`, read back
`1970-01-01T00:00:00` with `tm_isdst` 0.  That establishes the handle pairing
and the `time_t`/`struct tm` agreement, and nothing more — not a version, not
the rule data, not a zone file.  `README.zig.md`, "External ABI", has the full
provider contract.

Per file, not one label.  Upstream tz code and data are public domain except
`strftime.c`, `date.c` and `newstrftime.3`, which are BSD-3-Clause;
